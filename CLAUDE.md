# MasterMagic (working title)

A heavily modified Master of Magic, forked from https://github.com/kazzmir/master-of-magic (BSD 3-Clause, keep the LICENSE and copyright notice). Go 1.27 + Ebiten. Not a Godot project: the Godot sections of the guides do not apply.

## Release plan (user decision, 2026-09-27)
- The user does not plan to host the mod. The likely path is contributing changes back to kazzmir's project, so keep features in small separate pieces (new files, few upstream edits) that could each become a pull request. Upstream squash merges short branches and does not use gofmt.
- The fork is public and already pushed. The user will contact the original author (kazzmir, project Discord) once there is enough for an official mod release. Before that release: give the mod its own name (Master of Magic is the rights holder's trademark), add a README line saying it is an independent modified fork, keep LICENSE and the copyright notice.

## Reference workflow: ReMoM (user decision 2026-09-27)
We keep building on this fork and rebuild any visual that does not match the original, using ReMoM as the reference instead of screenshots from the user.
- What it is: a C reconstruction of Master of Magic v1.31 from disassembly, https://github.com/jbalcomb/ReMoM. Cloned at `D:/Work/MasterMagic_open/_reference/ReMoM` (commit a9cc082, 2026-08-31), OUTSIDE this repo.
- LICENSE RULE: ReMoM has no license and derives from the original program. Read it for FACTS (positions, palette indexes, font numbers, shadow modes, thresholds, strings) and write our own code. Never copy its code, never commit any of it here. Say in a comment which ReMoM function the facts came from.
- The user's release plan stays on this fork (BSD). Switching base to ReMoM was considered and rejected: fixed 320x200 256 color buffer, global state, no license.
- How to match a screen:
  1. Find its draw function: `MoM/src/<Screen>.c` (Combat.c, CityScr.c, MainScr.c, MagicScr.c, ArmyList.c, ...), described in `doc/MoM-*.md`. Grep for a string shown on the screen.
  2. Read the text setup before each Print: `Set_Font_Style*(font, color block, ...)`, `Set_Font_Colors_15(font, colors)` (pixel value k of a glyph gets colors[k]; value 0 is the alias pixel), `Set_Outline_Color(n)`, `Set_Font_Spacing_Width(n)`. Shadow modes and their offsets: `MoX/src/Fonts.c` Print_Display.
  3. Read positions from `Print*(x, y, ...)` and `FLIC_Draw(x, y, picture)`; pictures from `LBX_Reload_Next(file, entry, ...)`.
  4. Resolve palette indexes to colors: indexes below 224 come from the game palette; 224 and up come from the palette embedded in the screen's own pictures. In our code: `lbxFile.GetPalette(entry)` on the screen's background picture gives both.
  5. Build the text with `font.MakeStyledFont(lbxFont, colors, shadow, shadowColor)` and `StyledFont.Print` (whole art pixel positions, the original's alignment rules). Our glyph images use palette index k + 1 for pixel value k; MakeStyledFont handles that.
  6. Capture ours and compare.
- Alignment rules of the original (now in StyledFont): width has no letter gap after the last letter; right aligned text ends ON x; centered text starts at x minus half the width rounded down.
- Not set up yet: running ReMoM itself. It has scripted input replay and a headless mode (`doc/Devel-HeMoM-Testing.md`, `showcase/README.md`), which could give pixel exact reference captures of any screen. Needs its release binary or a build (CMake, MSVC, SDL2).

## Fog fade (world map, user request 2026-09-28)
- `game/magic/game/fogfade.go`, switch `FogFade`. A change of the fog of war (revealed, or no longer seen) is spread over time ONE ART PIXEL AT A TIME: every art pixel of a tile waits a time of its own by chance (up to `FogFadeSpread` 0.22 s) and then fades from what it showed to what it shows (`FogFadePixelTime` 0.12 s; first 0.45 and 0.25, user: "faster, but with the same style", so both are changed together). ## Smooth pan law
- The mouse only reports whole internal pixels (Ebiten keeps a finer position internally but does not expose it), 60 times a second. The camera follows the mouse exactly; the map is drawn with `game.displayCamera()`, a view that glides toward the camera each frame (`PanSmoothTime`) and lands exactly on it after release. With no drag or zoom going on, `snapCameraToPixel` keeps the camera on whole screen pixels so the resting map is crisp.
- Any camera position between screen pixels is drawn through the canvas in `zoom.go`: the map is drawn on whole canvas pixels and the canvas is placed at the leftover fraction with the smooth filter. This also smooths the camera's own move animation.
- `PanGain` (1.25) scales mouse movement into map movement, so the map runs slightly ahead of the cursor. `PanBy` takes screen pixels of map movement, already scaled.
- The cursor glides with the same filter during a pan (`game/magic/game/pancursor.go`, hooked in through `mouse.SmoothPosition`; drawn between pixels by `mouse/smooth.go`). Outside a pan the cursor is drawn at the mouse with no delay. Test: `TestCursorGlideMovesEveryFrame`. Dev flag `-capture-cursor-at x,y` draws the cursor through the between pixels path.
- Release glide (`game/magic/game/pancoast.go`): the drag speed is measured over `PanVelocitySmoothTime`; on release above `PanCoastStartSpeed` the camera keeps moving and slows with `PanCoastTime` (coast distance is release speed times that). A new drag, a zoom or any other camera move ends it; hitting the top or bottom of the map kills vertical speed. Releasing a still mouse does not coast.
- Dev: `-capture-drag N -capture-drag-speed S` simulates a drag (the simulation replaces the real button, see `panSimulated`), then leaves 80 frames for the coast, and logs view, camera and coast speed.

## Draw scale law (native draw scale, 2026-09-27)
- ONE SWITCH: `display.NativeDrawScale` in `game/magic/display/drawscale.go`. False restores everything from before: draw at 3, Ebiten stretches, zoom 3x/2x/1x, pan blends between pixels. Verified by building with it off.
- The game draws at the window's REAL pixel size: Windows display scaling counts. The user's machine is at 150% (monitor 2560x1440 in Windows units, 3840x2160 real), so the 1776 x 1000 window is 2664 x 1500 real pixels and the draw scale there is 7. `display.Layout` (called from `MagicGame.Layout`) picks the largest whole scale that fits, returns the real pixel size so nothing is stretched, and centers the picture; leftover pixels are black margins (`frameX`, `frameY`). `ContentOffsetX/Y` include the margins; the cursor, the mouse drawing and the FPS counter follow them.
- Zoom (`game/magic/camera/levels.go`): `ZoomMax = 2520` so every whole screen pixel per art pixel is a whole camera zoom. Levels are whole numbers one apart from the draw scale down, `ZoomLevelCount` (5) of them, never below 1: 7x..3x on the user's window, 5x..1x at scale 5, 3x..1x at scale 3. A draw scale change snaps the zoom to the nearest level. `-capture-zoom N` is now screen pixels per art pixel.
- At the native scale the pan view and the gliding cursor are rounded to whole screen pixels (`display.BlendBetweenPixels`); the between pixels canvas only runs during zoom animation.
- Development runs draw at the scale the saved window would get (`DrawScaleForWindow`); `-scale N` forces one; `-scale -1` forces the native layout in the corner window. The log records every draw scale change with the device scale factor.
- Probe history: 17 screens at 3 and 5 laid out identically (sheets in `_build/probe`). Upstream controls drawn with vector lines (settings checkboxes, volume bar, Keys and resolution boxes) keep 1 real pixel borders and look thinner at high scales. Not probed: combat, new game and wizard screens, diplomacy, hero screens. The spellbook sizes two page images when it opens; a scale change while it is open shows them at the old size until reopened.
- Frame rate at scale 7 with Reveal All: 83 to 98, versus 69 to 88 at scale 3.
- Resolution list: with the native draw scale, `WindowScale` IS the draw scale and each entry is named by its real pixel size (2478 x 1400 is scale 7). `windowSizeFor` makes the Windows-unit window just large enough for the picture in real pixels, so no margins (test `TestResolutionListFitsExactly`, scaling 100% to 200%). Files saved before carry no `scale-is-draw-scale` key and are converted once in `FinishStartup` (first Update, when Windows scaling is known): old scale times scaling, floored (the user's 5 became 7). Development runs skip that and keep the corner window.
- Gray column at the world seam, fixed: `Camera.GetTileBounds` rounded negative columns toward zero and skipped the leftmost column whenever the view sat part way into a tile left of column 0 (common since the smooth pan). Now floors. Test `TestTileBoundsCoverTheLeftEdge`; dev flag `-capture-camera-x` places the camera for a capture. The in-game check was shown to fail on the old rounding.

## Camera moves
- `game/magic/game/cameramove.go`: every camera move of the game's own (right click, jump to a unit, spell targeting) runs through `doMoveCamera` -> `animateCameraTo`.
